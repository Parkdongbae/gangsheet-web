# GLM 웹앱 업그레이드 스킬

GLM-5.3으로 빠르게 만든 웹앱을, 동작을 깨지 않고 눈에 띄게 끌어올리는 절차다.
아래 "실제로 나온 문제"는 일반론이 아니라 DTF GangSheet Studio v0.4.0 → v0.5.1
업그레이드(2026-11-23)에서 직접 확인한 것들이다. 다른 프로젝트에서는 같은 문제가
있는지 **먼저 확인하고** 적용한다.

## 0. 역할 분담

| 일 | 담당 | 이유 |
|---|---|---|
| 진단, 원인 확정, 설계, 검증, 문서 | Claude | GLM은 문서를 만들지 못하고, 실행·관찰을 하지 않는다 |
| 범위가 닫힌 코드 생성 | GLM (`GLM -q`) | 계약이 분명한 단일 파일은 빠르게 뽑을 수 있다 |
| 기존 대형 파일의 부분 수정 | Claude | 주변 맥락과 기존 계약을 읽어야 한다 |

GLM 호출 규칙(전역 CLAUDE.md):

- `GLM -q {코드 생성 작업}` — 코드 전체를 표준 출력으로 돌려준다
- `-l {python|node|bash}` — 언어 지정
- `-o {경로/파일명}` — 파일로 바로 저장
- 프롬프트에 `@glm`, `-glm`, `--glm`이 있으면 GLM 모드가 자동으로 켜진다

GLM에 맡길 때는 아래를 프롬프트에 **전부** 넣는다. 빠지면 그럴듯하지만 맞지 않는 코드가 나온다.

1. 파일 하나, 책임 하나 (예: "픽셀 연산 순수 함수 모음, DOM 접근 금지")
2. 입출력 타입 — 기존 인터페이스를 그대로 붙여 넣는다
3. 지켜야 할 수치 (임계값, 단위, 반올림 규칙)
4. 쓰면 안 되는 것 (새 의존성, 전역 상태, `any`)
5. 같은 호출에서 테스트 파일도 요구한다

받은 코드는 그대로 믿지 않는다. 타입체크 → 테스트 → 실제 실행 순으로 확인한 뒤 합친다.

## 1. 착수 전 진단 (코드를 고치기 전에)

1. **실행해서 본다.** 개발 서버를 띄우고 시작 화면과 주 화면을 스크린샷으로 확인한다.
   코드만 읽으면 레이아웃이 깨진 것을 놓친다.
2. **사용자가 겪은 실패를 재현한다.** 사용자가 준 자료(스크린샷, 파일)를 그대로 넣어
   같은 결과가 나오는지 본다. 재현되기 전에는 원인을 단정하지 않는다.
3. **프로젝트 문서와 코드를 대조한다.** `.agent/`, `README`, `summary.md`를 읽되,
   적힌 내용이 현재 코드와 맞는지 확인한다. 낡은 문서는 흔하다.
4. **검증 수단을 파악한다.** 테스트·린트·타입체크·E2E 명령과, E2E가 의존하는
   셀렉터(버튼 이름, `title` 속성)를 적어 둔다. 개편 중에 이것들을 유지해야 한다.

### 이 프로젝트에서 실제로 나온 문제

| 증상 | 실제 원인 | 찾은 방법 |
|---|---|---|
| 여백이 붙고 굵은 글씨가 안 먹음 | 레이어 밖 전역 리셋(`* { margin:0; font-weight:normal }`)이 Tailwind 유틸을 전부 덮음 | 스크린샷에서 간격 이상 → CSS 진입 파일 확인 |
| "배경 제거"가 사진에서 엉망 | 이름만 배경 제거이고 실제로는 테두리 색 플러드필 | 사용자 사진으로 재현 → 구현 파일 읽기 |
| "업스케일"이 흐림 | AI가 아니라 캔버스 리샘플 | 같은 그림을 리샘플과 나란히 비교 |
| 글씨가 너무 작음 | `text-[10px]` 위주의 고밀도 UI | 클래스 사용 빈도 집계 |
| 버튼이 줄바꿈되며 겹침 | 떠 있는 한 줄 툴바에 버튼 16개 | 1,440px 화면 스크린샷 |
| 문서가 코드와 다름 | "배경 제거는 v2 범위"인데 이미 구현됨 | 문서 ↔ 코드 대조 |

교훈: **기능 이름을 믿지 말고 구현을 읽는다.** 이름과 실제 동작이 다른 자리가 품질
불만의 진짜 원인인 경우가 많다.

## 2. 개편 원칙

1. **로직은 그대로, 껍데기만 바꾼다.** 상태·이벤트 핸들러·좌표 계산은 건드리지 않고
   JSX 구조와 클래스만 바꾼다. 큰 컴포넌트(수천 줄)는 구간을 정해 치환한다.
2. **테마는 팔레트 변수로 뒤집는다.** 컴포넌트의 색 클래스를 일일이 고치지 않고,
   Tailwind v4 색 변수(`--color-zinc-*` 등)를 테마별로 재정의한다. 캔버스처럼 CSS로
   칠할 수 없는 곳만 테마 훅으로 분기한다.
3. **계약은 선택적으로만 넓힌다.** 공유 인터페이스에는 선택 필드·선택 메서드만
   추가해, 다른 구현(데스크톱 등)이 수정 없이 계속 맞도록 한다.
4. **E2E 셀렉터를 유지한다.** 버튼 이름이나 `title`을 바꿔야 하면 E2E도 같은 커밋에서 고친다.
5. **이름과 실제를 맞춘다.** 가짜 구현을 진짜로 바꾸거나, 바꿀 수 없으면 화면 문구를
   실제 동작에 맞게 고친다.
6. **외부에서 받아 쓰는 것은 출처와 라이선스를 확인하고 리비전을 고정한다.**
   (모델 가중치, CDN 자산 등) 라이선스 고지 파일도 함께 갱신한다.

## 3. 검증 (가장 자주 빠지는 단계)

- [ ] 타입체크, 린트, 단위 테스트
- [ ] **배포용 빌드**로 띄워서 핵심 기능을 실제로 실행한다
- [ ] 실제 브라우저에서 사용자가 겪은 실패가 사라졌는지 확인한다
- [ ] 걸린 시간·크기 같은 수치는 재서 적는다
- [ ] 확인하지 못한 환경은 "미검증"이라고 적는다

**개발 서버 통과는 배포 통과가 아니다.** 이 프로젝트에서 AI 배경 제거는 개발
서버에서는 정상이었지만 배포 빌드에서는 "AI 준비 중"에서 멈췄다. 번들러가 추론
런타임을 워커 청크에 합치면서 스레드 워커가 엉뚱한 스크립트를 띄운 것이 원인이었고,
배포용 빌드를 띄워 보기 전에는 드러나지 않았다. 워커·WASM·동적 import가 들어간
변경은 반드시 `build` + `preview`로 확인한다.

오래 걸릴 수 있는 작업에는 처음부터 넣는다.

- 진행률(%)과 남은 시간
- 제한 시간과 그 뒤의 대체 경로
- 실패했을 때 사용자가 할 수 있는 일을 알려주는 문구

## 4. 마무리

1. 사용자 문서(매뉴얼, README)와 라이선스 고지를 실제 동작에 맞춘다.
2. 프로젝트 규칙의 진행 기록(`summary.md` 등)에 **원인·수정·검증·미검증**을 남긴다.
3. 프로젝트 규칙의 브랜치로 커밋·푸시한다. 푸시가 곧 배포인 저장소라면 3장의
   배포 빌드 검증을 끝낸 뒤에만 올린다.
4. 사용자에게 보고할 때는 고친 것과 확인하지 못한 것을 나눠 적는다.

## 5. 빠른 점검표

- [ ] 실행해서 화면을 봤다
- [ ] 사용자의 실패를 같은 입력으로 재현했다
- [ ] 문서와 코드가 다른 곳을 찾았다
- [ ] 이름과 구현이 다른 기능을 찾았다
- [ ] 전역 CSS가 유틸 클래스를 덮지 않는지 확인했다
- [ ] 로직을 건드리지 않고 화면만 바꿨다
- [ ] GLM에 맡긴 코드는 타입·테스트·실행으로 확인했다
- [ ] 배포용 빌드에서 핵심 기능을 실행했다
- [ ] 문서·라이선스·진행 기록을 갱신했다
- [ ] 미검증 항목을 보고에 적었다
